Step 5 requires hysteresis that stops a task being thrown back and forth between devices and providers. TWO DAMPING RULES ARE IMPLEMENTED BECAUSE THEY DEFEAT TWO DIFFERENT OSCILLATIONS, and that is the design judgement of this increment. PERSISTENCE requires the same alternative observed min_consecutive_confirmations times running, so one noisy sample never relocates work; the counter is kept per ALTERNATIVE, so an ABAB pool resets to 1 every time. DWELL requires min_dwell_ms since the last switch even once persistence is satisfied, and this is the rule that actually kills flapping: under persistence ALONE an alternating pool still switches once per pair, whereas the dwell bounds the switch RATE. A test alternates six times and asserts the task never moved, and a companion test shows a persistent alternative being SUPPRESSED at zero elapsed time and then switching once the dwell is met. FURTHER DECISIONS RECORDED RATHER THAN LEFT IMPLICIT. The first selection is ADOPTED immediately rather than damped, because it is not a flap and damping it would only add latency. With no eligible candidate the decision is HOLD rather than moving to nothing, since swapping to nothing is not a decision, and an ineligible named candidate is likewise held because eligibility is what licenses a move. Subjects are damped INDEPENDENTLY, so one noisy task cannot suppress another. # RS-202 — 多设备并发感知与再调度

> **常驻施工规则：** [../CONSTRUCTION_RULES.md](../CONSTRUCTION_RULES.md)  
> **过程数据规则：** [../PROCESS_DATA_POLICY.md](../PROCESS_DATA_POLICY.md)  
> 本工作书只定义任务特有 scope / dependency / acceptance；通用 claim、等待/唤醒、CI、双机独立与 merge 规则以常驻规则书为准。

## 目标
解决多设备同时向同一 AI/provider/session 发起交互时响应明显变慢的问题：感知设备、会话、provider 与本地主机压力，在用户不切换 provider 时做安全再调度，而不是让所有请求继续撞同一条拥塞路径。

## 已确认行为方向
- 设备数量动态；
- provider/model 池动态；
- 用户可先选择是否切换其他 AI；
- 若不切换，再进入 scheduler 的排队/分流；
- 临时无可领取/无可调度资源不是“任务结束”，需要 eligibility-aware bounded re-scan；
- 没资格领取与暂时没有资源必须分开；
- 结果必须回当前交互设备，不要求用户走到执行设备。

## 允许修改边界
scheduler/foreman、routing、device telemetry/presence、queue/lease、load model、相关 contracts/tests。

## 禁止修改边界
- 不重新设计 UI；
- 不把 CPU/GPU 一项指标粗暴等同“设备忙”；
- 不跨越 Remote Fabric trust/permission；
- 不把并发冲突靠无限 sleep/轮询解决；
- 不因为当前无空闲 provider 就丢弃请求。

## 施工步骤
1. 审核现有 EM-010 foreman scheduler、GAI routing、Remote device/presence contracts。
2. 定义可解释的 pressure/eligibility 输入：当前 session/provider concurrency、设备运行负荷、设备可达性、policy、用户禁用等。
3. 建立 routing sequence：本设备/当前 provider 可直接运行 → 提供 provider switch choice → 用户不切换时 scheduler queue/alternate eligible device → bounded retry。
4. 临时 zero-claim 使用约 20 分钟级别的 bounded re-scan 语义作为上限策略参考，但实现必须事件驱动优先，避免死等。
5. 建立 anti-flap/hysteresis，防止任务在设备/provider 间来回抖动。
6. 覆盖多个设备同时提交、一个设备高负载、一个 provider session 拥塞、设备离线恢复、eligible set 从 0 变 1。

## 独立复核
另一台主机做 race/adversarial test：重复调度、双执行、stale telemetry、lease 过期、设备突然离线、queue starvation、re-scan 风暴、同一用户多设备并发公平性。

## 完成门槛
- 并发压力能影响调度但不会改写权限；
- 不切换 provider 时仍有明确的排队/跨设备路径；
- transient no-resource 不被误判 terminal failure；
- anti-flap 与 single-execution/idempotency 可证明；
- hosted CI 全绿。
