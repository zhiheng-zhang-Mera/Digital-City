# DGX — Deliberative Governance Expansion & Migration

## Goal

Add a cross-domain Deliberative Governance / Adjudication institutional layer without demolishing the City structure, moving accepted capabilities or creating a second task truth:

```text
Owner request
→ semantic decomposition
→ Shared Fact Snapshot
→ Problem Graph / DAG
→ bounded Task Capsules
→ capability/history + independence assignment
→ isolated execution
→ structured Result / Evidence Envelopes
→ integration
→ conflict detection
→ defence / rebuttal
→ fresh-context independent adjudication
→ appeal / minority dissent when applicable
→ participant final review
→ release gate
→ Process Capsule to Owner
```

Problem Graph is a deliberation plan/problem structure, not another Mission Book, scheduler or runtime task authority. Only actions formally accepted by existing task/runtime contracts become execution facts.

## Core contracts after the second fusion

### 1. Shared Fact Snapshot

Parallel participants should start from the same versioned fact snapshot wherever possible:

- Owner request / accepted requirement.
- Canonical task/capability/runtime facts.
- Exact evidence references.
- Domain constraints.
- Known unknowns / unavailable evidence.

Snapshots contain explicit auditable information only, never participants' hidden chain-of-thought.

### 2. Problem Graph / Task Capsule

Complex requests may decompose into a DAG, rather than a mandatory fixed tree:

- A node is a bounded question, verification or integration task.
- An edge is a dependency, evidence relation, contradiction or prerequisite.
- Nodes may expand under control after discovering new facts.
- Every Task Capsule declares scope, inputs, required capability, independence floor, expected output and stop condition.

### 3. Isolated execution and structured exchange

Parallel Agents do not synchronize by sharing hidden reasoning. Default exchange consists of:

- Structured results.
- Explicit assumptions.
- Evidence references.
- Confidence/uncertainty, where observable.
- Unresolved questions.
- Proposed next action.

This preserves independence while permitting subsequent integration and audit.

### 4. Independence profile

DGX declares task/role independence needs without lowering any existing domain gate. Candidate dimensions include:

- Role / authorship independence.
- Agent / session-context independence.
- Model-family independence, where needed.
- Host / environment independence.
- Hardware/toolchain independence.
- Conflict of interest / recusal.

Engineering Formal Review still follows the different-physical-host requirement of `CONSTRUCTION_RULES.md §3`. Same-host fresh critics may diagnose only; DGX's existence cannot upgrade them to Formal Review.

### 5. Fresh-context adjudication

Prefer two stages for governance adjudication of material conflicts:

```text
Phase A: independent reconstruction
  requirement + accepted facts + evidence
  → provisional findings

Phase B: reconciliation
  open defence / rebuttal / alternative interpretation
  → final adjudication receipt
```

This is an independence protocol for governance adjudication. It does not automatically replace Engineering/Research/Health Formal Review.

- **City Work Monitor / Control Centre:** user projection of governance processes, not a second task truth.

## User transparency principles

The Process Capsule returned to Owner by default answers at least:

1. How the request became a problem graph.
2. Which Agents/roles participated.
3. Why assignment was made this way and which independence floor applied.
4. Each node's explicit results/evidence.
5. Whether material conflicts occurred.
6. How conflicts were adjudicated.
7. Which validations were performed.
8. What residual uncertainty remains.
9. Whether Final Release Gate passed.

Do not require Owner to read routine heartbeats, repeated logs, every token, unused candidate drafts or hidden chain-of-thought. Deeper evidence expands on demand through Monitor progressive disclosure.

```text
KEEP IN PLACE

→ add governance metadata / adapters
→ migrate implementation only on demonstrated ownership duplication/conflict
```

Do not move implementations already accepted by exact-head/opposite-host review merely for architectural neatness.
