## 5. ⚠ Cross-Mission merge conflict and ruling

### 5.1 Facts

Merging main, already containing MB-001/002/004/005/006, with MB-009 produced three conflicts; the third was semantic:

1. Manifest auto-merge created two foundation districts. Branch base c7ef3cd1 had none, so MB-009 created one; main already had MB-001's. Git retained both, yielding an invalid duplicate ID. They were combined into one, preserving metadata and ordering buildings by ascending ID.
2. Registry retains MB-002's fabric-backed ADAPTER_PROVIDERS and points the theme reference at its relocated path.
3. The move directly conflicts with MB-001's invariant. Foundation is infrastructure and its modules were excluded from the resolution index. MB-009's mandatory City-map path therefore produced:

{{CODE3}}

This breaks both MB-009's existing callable Theme Generate gate and main's accepted five-service surface.

### 5.2 Reasoning

Two City statements conflict: MB-001 says foundation is the runtime kernel and its modules are not capabilities; the City map says 00/05 owns presentation/theming. The problem is district-level kind granularity: foundation now contains kernel buildings and one genuine adapter-bridged capability building.

Rejected options: changing the district kind exposes unavailable kernel capabilities and breaks MB-001; moving theme elsewhere violates Mission ownership; deleting or relaxing MB-001 tests is forbidden by rule 11.

### 5.3 Ruling

Refine kind to the building level, inheriting the district by default:

| File | Change |
|---|---|
| city/manifest.mjs | Validate building.kind with DISTRICT_KINDS; export buildingKind(district, building) as the sole decision point and declaredBuildings(manifest). |
| CITY_IMPLEMENTATION_MANIFEST.json | Declare 00-foundation/05-control-centre kind:domain. |
| registry.mjs | Resolution index covers every declared module so explicit bridges resolve. Enumeration still excludes infrastructure buildings and capabilityProvider:false. |
| capability-registry.test.mjs | Assert kernel properties per building's effective kind; add assertions that control-centre differs from its district and theme is AVAILABLE. |

This is not relaxation: all previous inputs behave identically because no building previously declared kind; kernel city-core/fabric assertions are retained and additional root-cause/restoration assertions strengthen them; no City ownership or product capability is added. It repairs a regression, rather than merely making a failure green.

Measured after merge: seven descriptors, five AVAILABLE, presentation.theme.lab AVAILABLE, theme-engine visible in Web/Android's callable list and successfully generating, section 3.4.

### 5.4 Owner visibility

The ruling changes shared files and tests introduced by MB-001, so the Owner should know even though it is strictly conservative. Options: accept building-level kind as a City mechanism (recommended, satisfying both statements); or, if foundation should not contain capability buildings, the Owner should repartition ownership and create a superseding Mission. The verifier must not make that ownership decision.
