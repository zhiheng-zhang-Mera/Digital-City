# UI-000 — Visual candidates and aesthetic gate

> [Persistent construction rules](../../../../CONSTRUCTION_RULES.md) · [Process data policy](../../../../PROCESS_DATA_POLICY.md). This workbook defines task-specific scope/dependency/acceptance only; persistent rules govern ordinary claims, waiting/wake, CI, independent two-host work and merging.

## Goal

Build three distinctly different, directly comparable visual product candidates from actual Utopia code/functions. Owner does not write design specs, only chooses A/B/C; if none appeals, one natural-language reason suffices.

## Confirmed context

Three current surfaces: apps/web/** Vanilla HTML/CSS/JS; apps/android/** Kotlin + Jetpack Compose Material 3; apps/rooms/** Vanilla HTML/CSS/JS Room Hub.

Main problem exceeds color: engineering structure directly appears in navigation/content—nine Android primary entries, Web control-surface/dashboard vocabulary, raw Action/Provenance/route, Rooms black/cyan developer-tool visuals.

### Mandatory UI rules

- Ordinary user interfaces must depart from dashboard/admin/terminal/developer-console appearance.
- Internal module names, IDs, routes, backendRef, provenance, schema/version and runtime paths collapse into Advanced information / Runtime details by default.
- Do not substitute stacks of uniform rounded cards for information architecture.
- Do not use ASCII/Unicode geometric symbols as the formal icon system.
- Do not migrate Web/Rooms to React/Vite/shadcn; Android stays Compose Material 3.
- Do not change existing Gateway / Action / Ask / Task / Room API / Scheduler semantics.
- Hns may autonomously download/install/replace UI/UX, Compose, browser, screenshot-comparison, accessibility and Agent Skill plugins. Plugins belong to construction tooling by default; record source/ref in reports. Do not upload secrets or make unknown plugins production runtime dependencies.

## Allowed change boundary

- Temporary candidate branches/design tokens/prototypes.
- Presentation-only changes for real candidates.
- Real-page screenshots with static/safe existing-API data.
- Pure design docs, screenshot scripts, visual-test helpers.

## Prohibited change boundary

- No new business capability.
- No API/protocol/DTO change.
- No framework migration under candidate-design pretext.
- Do not retain all three candidates permanently in production.

## Construction steps

1. Read Web/Android/Rooms UI/key interactions; produce function/information map.
2. Automatically form three structurally and visually distinct candidates, e.g. Personal OS/Ambient AI/Personal Control; names may vary.
3. All share identical function facts; do not remove functionality to fake simplicity.
4. Each includes real Home, Ask/Do, Tools/Rooms pages, representative Android page and one Room page.
5. Real code or high-fidelity running prototypes, not only moodboard/prose.
6. After developer self-evaluation, opposite host independently critiques visuals and may directly repair clear defects.
7. Submit A/B/C + screenshots only when all three are comparable; do not ask font/radius/color details.

## Independent review

Check true differentiation rather than recoloring; retained core functions; lingering engineering/monitor style; mobile/desktop legibility; generic AI SaaS template copying; technical details demoted by default yet reachable.

## Completion gates

- Three real candidates complete.
- Representative Web/Android/Room evidence.
- Opposite-host independent review complete.
- Owner only selects A/B/C or says none looks good.
- Record choice in UI-000 report as sole visual-direction source for UI-101..103.

## Binding persistent rules

Inherit [CONSTRUCTION_RULES.md](../../../../CONSTRUCTION_RULES.md). In particular: Development and Review of one task use different physical hosts; waiting does not occupy a host; zero claims must be classified; WAITING_ELIGIBILITY prioritizes event wake with approximately 20-minute fallback rescans; external recovery requires reconciliation; CI/evidence bind exact head; no make-work or unilateral scope expansion.

- Raw screenshots, browser traces, Android physical-device evidence and failed retries remain in Utopia runtime/evidence; research-relevant structured events enter evolution under PROCESS_DATA_POLICY.
