# Digital City 协议

本文定义 Digital-City 的架构词汇和最低集成规则。

## 1. 先按项目分解，再耦合

默认审查单位是**已有仓库**，不是设想的城市模块。

对每个待审仓库：
1. 恢复其原始目的和当前实现范围；
2. 分解为内聚的能力群；
3. 用下述城市词汇分类各能力群；
4. 将能力群放入适当区／建筑／房间；
5. 仅为真实跨边界交互定义道路；
6. 直到有实现／测试／生命周期收益才物理抽取代码；
7. 仅在已有项目审查后必要能力仍无所有者时创建新占位。

仓库**不等于建筑**。它可支持一座或多座建筑，也可向多个区贡献有边界模块；反过来，一座建筑可由多个仓库支持。城市位置记录架构所有权，仓库位置记录实现溯源。

每个分解出的能力群须分类：

| 类型 | 含义 | 典型所有者 |
|---|---|---|
| 城市基础设施 | 运行时、信任、身份、编排、节点网络、能力网络、语义道路、共享生命周期和人类控制界面 | 城市级基础设施 |
| 区 | 一级领域／市政分组，组织相关建筑而不合并其实现 | Digital-City 拓扑 |
| 建筑 | 区内内聚的机构／产品／服务边界；可由一个仓库、多个仓库或明确占位支持 | 所属项目／产品边界 |
| 规划建筑 | 尚无实现的预留城市位置 | 仅 Digital-City 文档 |
| 房间 | 某建筑拥有的能力 | 该仓库内模块／服务 |
| 居民 | 使用城市服务的持久数字身份／代理 | Digital-Me 或未来代理 |
| 道路 | 建筑之间稳定接口、事件、模式或数据流 | 共享契约 |
| 桥梁 | 跨多条道路／建筑的较高层集成 | 明确跨项目组合 |
| 工程施工 | 建设、修复、资格验证、主机与恢复工具 | DS-Hns 和运维仓库 |

Capability Fabric 与 Node Fabric 有区别：Node Fabric 回答存在哪些已授权运行时节点；Capability Fabric 回答存在哪些能力、谁提供、如何发现／注册。插件只是能力包装／准入的一种形式，不是能力模型本身。

不能仅因多个项目使用某特征就将其移入 Boss；只有真正城市级基础设施才属于 Boss。

规划建筑必须明确使用 `PROJECT_NOT_CREATED` 状态。占位仅预留拓扑，没有实现权威。

**反追逐规则：** Digital-City 不得先发明模块再到 GitHub 寻找项目来证明它合理。正常路径是分解已有项目；先占位的设计仅用于明确必要、且无已审仓库拥有的能力。

## 2. 仓库独立性

Digital-City 是注册表与集成地图，不是单体仓库。

连接仓库应保持：
- 可独立克隆；
- 可独立测试；
- 可独立版本管理；
- 适用时可独立发布；
- 能描述其公开的城市房间与道路；
- 实际可行时可移除／替换而不强迫无关领域重写。

Digital-City 不得成为其源码树副本。

## 3. 真值来源

- 项目实现真值在项目仓库。
- 城市位置和跨项目角色在 Digital-City。
- 区 README 向人解释区边界。
- 建筑 README 解释建筑边界及其公开城市能力。
- `CITY_MANIFEST.yaml` 为机器描述同一拓扑。
- 项目专属证据留在项目中，除非明确需要城市级账本。
- 规划占位绝不是实现真值。

## 4. 道路

当两个项目反复交互时，应明确道路。

道路最终应声明：
- 生产者与消费者；
- 载荷／模式；
- 认证／身份语义；
- 权限边界；
- 失败语义；
- 相关时的重试／幂等行为；
- 溯源／证据要求；
- 版本兼容性。

当前概念道路类别：
1. 身份道路（Identity Road）
2. 能力道路（Capability Road）
3. 事件道路（Event Road）
4. 证据道路（Evidence Road）
5. 数据道路（Data Road）
6. 策略道路（Policy Road）
7. 学习道路（Learning Road）
8. 恢复道路（Recovery Road）

探索时可容许临时直接耦合，但不应无声地成为永久基础设施。

## 5. 治理与策略范围

Digital-City 将规则范围与执行权威分开。

### L0 — 城市宪法

仅保留极少量城市级不变量，例如：
- 根身份与 Owner 主权；
- 明确的权威移交边界；
- 跨域权限／范围隔离；
- 受保护数据边界；
- 审计／溯源完整性；
- 城市级扩展生命周期及安全移除。

城市宪法必须保持精简。研究、健康、建设或娱乐等域专属规则不属于此层。

### L1 — 领域章程

各域可定义自身规则，例如：
- 研究：模型语义、可证伪性、证据及研究评审规则；
- 医疗：健康数据处理和健康模型证据要求；
- 工程：建设、修复、连续性和运维约束；
- 娱乐：媒体／体验专属行为。

> **除非明确提升，策略按领域限定范围。**

研究章程不会自动治理医疗或 Hns，医疗规则不会自动治理研究；提升为城市级范围必须明确。

### L2 — 项目策略

具体仓库／建筑可在其领域边界内定义本地策略。

### L3 — 运行时／实验规则

临时门禁、实验设置、版本专属检查和执行规则保持本地，除非有意提升。

## 6. 准入、执行与审计

城市使用三个概念动作，不建立新的官僚层：

```text
ADMIT   = 此建筑／扩展能否安全进入？
ENFORCE = 运行时是否违反城市级硬边界？
RECORD  = 发生了什么，涉及何种身份／权威／证据？
```

### 海关安检 / Customs Security — ADMIT

未来海关安检能力可验证：
- manifest／模式；
- 身份／来源；
- 依赖；
- 请求权限／能力；
- 领域范围；
- 隔离；
- 启用／禁用／卸载／回滚语义。

它是准入时边界，不应持续治理已准入建筑内部业务逻辑。

### 公安与运行时合规 / Runtime Compliance / Public Security — ENFORCE

未来运行时合规能力可在有意义的执行点实施城市级硬边界，例如：
- 特权请求；
- 跨域调用；
- 受保护数据访问；
- 持久状态修改；
- 服务注册；
- 权威升级。

它不得评判领域质量。它可阻止研究读取受保护医疗数据，但不判断研究模型科学正确性、健康估计临床质量或 Hns 调度最优性。

### 审计 — RECORD

审计记录身份、权威、决策和证据，不成为另一审批层。

## 7. 研究与机器智能范围

面向博士研究的机器智能方向当前是**研究域计划**，不是城市宪法原语。

候选机制：
- 延迟／学习后巩固；
- 熟悉度／融合状态；
- 动态关联结构；
- 长期适应；
- AI 辅助数学形式化；
- 多 AI 批评；
- 模拟与可证伪预测。

若以后证明稳定且真正可跨域复用，这些机制可被提升。在此之前：

```text
研究机制 != 城市核心要求
研究章程 != 城市宪法
研究结果 != 自动运行时真值
```

Boss 可提供多个域需要的通用原语，研究专属语义仍留在研究域。

## 8. 仓库审查与建筑准入

先审查仓库，再发明新拓扑。

既有仓库审查结果可为：
- `CITY_OWNED_MODULES`：一个或多个能力群有明确城市位置；
- `REFERENCE_OR_DONOR`：有用实现／证据谱系，但非永久所有者；
- `ENGINEERING_OR_TOOLING`：运维支持，非领域建筑；
- `HISTORICAL_OR_COURSEWORK`：保留但不纳入活跃城市拓扑；
- `REVIEW_PENDING`：尚未决定位置。

至少满足下列一项时，可注册为连接仓库：
- 拥有活跃城市能力；
- 另一城市项目依赖它；
- 它是城市能力的规范证据／研究产物；
- 提供可复用工程、设备、隐私或领域基础设施。

**规划建筑占位**仅在以下条件下可先于仓库注册：
- 预期城市角色明确；
- 明确标为 `PROJECT_NOT_CREATED`；
- 没有活跃依赖将其当作已有实现；
- 专用仓库创建延后至真实实现工作足以支持它。

旧课程作业和无关实验不会自动准入。

## 9. 扩展原则

未来生态接入应优先采用薄扩展契约，而非修改城市核心。

未来扩展接口只应回答例如：
- 身份／版本；
- 请求能力和权限；
- 所需服务／依赖；
- 领域范围；
- 存储命名空间；
- 生命周期：安装／启用／禁用／卸载／回滚；
- 崩溃／隔离边界。

新生态通常不应要求重设计 Root Trust、建立新 epoch 仪式或迁移无关领域。

## 10. 更新纪律

城市拓扑变化时：
1. 更新受影响区和／或建筑 README；
2. 更新 `CITY_MANIFEST.yaml`；
3. 若影响导航或城市级语义，更新根城市地图；
4. 新跨项目依赖成为持久关系时更新道路文档；
5. 一旦其他工具依赖路径，不随意重命名区／建筑；
6. 在项目存在前明确保持占位非运行状态；
7. 不仅为便利而提升领域规则至城市级范围。
